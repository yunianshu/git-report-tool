# Spec：数据库备份配置按部署环境独立

## 背景与目标

同一个项目可以配置多个部署环境（测试 / 生产 / 多台服务器），各环境是彼此独立的服务器与数据库实例。
但数据库备份配置（是否备份、类型、容器名、库名、用户）此前存放在**项目级** `deploy` 上，
发布到测试环境与发布到生产环境用的是同一份配置——一旦两个环境都启用备份，必然把 A 环境的容器名/库名
用到 B 环境（备份错库或直接失败），使「多环境」在最关键的数据库链路上不成立。

本功能把数据库备份配置下沉到部署目标级别（`targets[].db`），并在读取时自动迁移旧格式。

## 业务规则

### R1 环境级存储
- 数据库备份配置存放于每个部署目标：`targets[].db = { enabled, type, container, name, user }`。
- 项目级 `deploy` 不再包含 `backupDatabase/dbType/dbContainer/dbName/dbUser`；其余发布策略
  （备份代码/失败自动回滚/成功后删除上传包/保留份数）保持项目级——它们是不含环境特定值的统一策略。
- 验收：[打开部署设置] → [出现「数据库备份（当前目标）」卡片；「部署选项」卡片内不再有该组配置]

### R2 旧配置迁移
- 旧格式（项目级 `deploy.backupDatabase/dbType/dbContainer/dbName/dbUser`）在读取时必须迁移到该项目的
  **每个**部署目标；迁移后项目级不再保留这些键（避免两份真源）。
- 目标自身已有 `db` 时以目标值为准，不被项目级旧值覆盖。
- 迁移幂等：保存回写后配置仍在环境上，不丢失、不重复迁移。
- 验收：[旧格式项目] → [部署设置中每个环境都显示迁移后的容器名/库名且开关为启用；保存后项目级无残留]

### R3 发布 / 备份 / 恢复按当前环境
- 发布时传给部署脚本的 `--db-container/--db-name/--db-type/--db-user` 取自**当前目标**；未启用备份的目标传 `--no-backup-db`，不得带上其他目标的库参数。
- 发布前本地校验按当前目标拦截缺容器名/库名，错误信息标明所属环境。
- 「数据库备份」列表与一键恢复按当前目标的配置执行（未启用的环境拒绝恢复）。
- 验收：[测试环境启用 pg-test/db_test，生产环境未启用] → [切到测试发布带 `--backup-db --db-container pg-test`（校验通过）；切到生产发布为 `--no-backup-db`、恢复被拒并提示未启用]

### R4 界面归属与随环境切换
- 数据库备份配置在「部署设置」中按「数据库备份（当前目标）」卡片编辑；切换环境时显示该环境自己的值。
- 发布卡「数据库备份」按钮按当前环境显隐：该环境启用备份才出现。
- 验收：[切到启用备份的环境 → 按钮出现；切到未启用环境 → 按钮消失，且两环境配置互不覆盖]

### R5 复制与默认带入
- 「从其他项目复制」与新建项目默认带入按 R1-R3 规则复制：各环境的 `db` 配置跟随各自的环境，不做项目级合并。

## 职责边界（不做什么）

- 不改凭据加密方案；`db` 内不含凭据（数据库账号密码仍由数据同步/SSH 链路管理）。
- 不把备份代码/自动回滚/保留份数下沉到环境（本期只处理带环境特定值的一组）。
- 不做 MySQL 的一键恢复（沿用现状：仅 PostgreSQL 支持恢复）。

## 验证手段

- 纯逻辑：`scripts/deploy-selftest.cjs`（发布参数取自当前目标、多环境不串台）、
  `.sdd/specs/deploy_copy/verify-copyconfig.cjs`（环境级配置随环境复制、旧格式迁移与幂等）。
- 端到端：`scripts/deploy-env-db-e2e.cjs`（真实 Electron + 沙箱主目录：迁移可见、切环境编辑互不覆盖、
  保存落盘到各自环境、二启基线不脏、发布页按钮随环境显隐）。
- 服务端链路：`scripts/deploy-datasync-selftest.cjs`（数据库恢复按当前目标配置执行）。
